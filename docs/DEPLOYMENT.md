# Deployment

The app is a standard Next.js 16 application with one external dependency —
PostgreSQL — and one scheduled job. It runs on Vercel, on any Node host, or
in a container. Nothing in the code is Vercel-specific; `src/lib/site.ts`
reads Vercel's URL variables when they exist and falls back cleanly when they
do not.

## What a deployment needs

| Requirement | Why |
|---|---|
| Node 20+ | Next.js 16 baseline |
| PostgreSQL 16 | `Json` columns, `@db.Date`, `bytea` receipts, `groupBy` reports |
| `DATABASE_URL`, `AUTH_SECRET` | The app will not run without them |
| `CRON_SECRET` + a schedule | Kitchen release on time rather than on page load |
| `NEXT_PUBLIC_APP_URL` | Canonical URLs on the real domain |
| TLS | Session cookies are `Secure` when the request arrives over HTTPS |

## Deploying to Vercel

**1. Provision a database.** Vercel Postgres, Neon, Supabase or any managed
Postgres. Take the **pooled** connection string if the provider offers one:
serverless functions open many short-lived connections and a direct
connection limit is reached quickly. Add `?sslmode=require`.

**2. Import the repository** at vercel.com/new.

> If the repository is private and owned by a GitHub organization, importing
> it needs a Vercel **Pro** team — the Hobby plan refuses with
> `repo_owned_by_org`. Either upgrade the team, transfer the repository to a
> personal account, or make it public.

**3. Set the environment variables** in Project → Settings → Environment
Variables, for Production and Preview:

```
DATABASE_URL         postgresql://…?sslmode=require
AUTH_SECRET          <openssl rand -hex 32>
CRON_SECRET          <a different openssl rand -hex 32>
NEXT_PUBLIC_APP_URL  https://your-domain.com
```

**4. Set the build command** so migrations run before the build:

```
prisma migrate deploy && next build
```

The Prisma client is generated by the explicit `postinstall` script in
`package.json`. That script is there rather than left to `@prisma/client`'s
own postinstall because Vercel caches `node_modules` between builds: when the
cache hits, `npm install` does not run, and a schema change would otherwise
build against a stale generated client.

`migrate deploy` applies only the migrations committed to the repository; it
never invents one and never drops data.

**5. Deploy.** The cron schedule in `vercel.json` is picked up automatically:

```json
{ "crons": [{ "path": "/api/cron/release-orders", "schedule": "*/5 * * * *" }] }
```

Vercel sends the project's `CRON_SECRET` as a bearer token. Five minutes is
the tightest interval available below Pro, and it is comfortably inside the
tolerance that matters — an order released four minutes late still leaves the
full prep window intact, because release time is computed from pickup time,
not from when the job happened to run.

**6. Seed the restaurant row.** The app needs one `Restaurant` record to
start. Either run the seed once against the production database:

```bash
DATABASE_URL="<production url>" npm run db:seed
```

…or, for a real launch, run it and then replace every seeded value from the
admin panel — see `docs/HANDOVER.md`. Immediately after, create real staff
accounts and delete the demo ones:

```bash
DATABASE_URL="<production url>" npm run staff:create
```

**7. Verify.** Walk `docs/QA-CHECKLIST.md`. The three that catch the most:
staff login actually signs in (proves cookies are `Secure`-correct behind the
proxy), a scheduled order reaches the kitchen board without anyone loading a
page (proves cron auth works), and the menu renders in Arabic RTL.

## Deploying anywhere else

```bash
npm ci
npx prisma migrate deploy
npm run build
npm start                 # listens on $PORT, default 3000
```

Put it behind a TLS-terminating reverse proxy that sets `x-forwarded-proto`
and `x-forwarded-host`. The app reads both, and gets cookie `Secure` flags,
CSP `upgrade-insecure-requests` and redirect origins right from them — see
`docs/DECISIONS.md`.

For the cron job, any scheduler works; the endpoint accepts GET and POST:

```cron
*/5 * * * * curl -fsS -H "Authorization: Bearer $CRON_SECRET" \
  https://your-domain.com/api/cron/release-orders
```

### Docker sketch

```dockerfile
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npx prisma generate && npm run build

FROM node:20-alpine
WORKDIR /app
COPY --from=build /app ./
ENV NODE_ENV=production
EXPOSE 3000
CMD ["sh", "-c", "npx prisma migrate deploy && npm start"]
```

Set `output: "standalone"` in `next.config.ts` first if you want a smaller
image; the app does not otherwise care.

## Rollback

Application rollback is the host's redeploy of a previous build. **Database
rollback is not automatic** and should not be assumed: `prisma migrate
deploy` moves forward only. Before any migration that drops or renames a
column, take a backup — the managed providers all offer point-in-time
restore, and turning it on is a one-time click that is worth more than any
amount of care afterwards.

## After the first deployment

- **Backups.** Enable them on the database. Nothing else in this system holds
  state — no uploads directory, no local files. The database is the whole
  product.
- **Error tracking.** `src/app/error.tsx` shows the digest of a failure,
  which is the handle that matches a user's report to a server log line. A
  hosted error tracker (Sentry and friends) is a drop-in addition; nothing
  here needs changing to accommodate one.
- **Uptime check.** Point it at `/` — it is a server-rendered page that
  touches the database, so a 200 means the whole stack is alive.
- **Rate limiting.** The in-process limiter enforces per-instance counts. If
  the deployment scales beyond one instance and abuse becomes real, move
  `src/lib/rate-limit.ts` to a shared store or enable the host's edge rate
  limiting. This is a single-file change (`docs/DECISIONS.md`).
